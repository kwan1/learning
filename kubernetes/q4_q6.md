## Q4 — Job: apply and verify

### Original failure
Correct YAML written, but never applied and never verified. Object was right; the evidence was missing.

### Second retake failure (variant question)
Question: *namespace `batch-ops`, Job named `log-writer`*. Collapsed the two literals into one — used `batch-ops` as the **Job name** and omitted the namespace entirely, so the Job landed in `default`. Also showed `kubectl logs` output without ever showing the Job reaching its required completions.

### Correct manifest

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: log-writer
  namespace: batch-ops
spec:
  completions: 3
  backoffLimit: 2
  template:
    spec:
      containers:
      - image: busybox
        name: log-writer-container
        command: ["echo", "processing", "complete"]
      restartPolicy: Never
```

Notes:
- `restartPolicy: Never` (or `OnFailure`) is **required** on a Job pod template — `Always` is rejected.
- Putting `namespace:` in the manifest is safer than relying on `-n` at apply time: the file is self-describing and you can't lose it by forgetting a flag. `kubectl logs` still needs `-n` regardless.
- `kubectl create job` has no `--completions` / `--backoff-limit` flags — scaffold with `--dry-run=client -o yaml`, then hand-edit.

### Verification — both halves

```bash
# 1. Job object reached required completions
kubectl get job log-writer -n batch-ops        # COMPLETIONS 3/3, STATUS Complete

# 2. Workload actually did its job
kubectl logs job/log-writer -n batch-ops       # "processing complete"
```

**Rule:** Jobs always have two verifications — the object completed, *and* the container produced the expected output. The question wording tells you which; usually it wants both.

## Q6 — RBAC: ClusterRole scoped to one namespace

### What went wrong, in order

1. **Wrong resources in the ClusterRole.** Created with `--resource=secrets,pods` instead of `services,pods`. Over-granted `secrets` (`list secrets` exposes credentials — one of the most sensitive grants in Kubernetes) and omitted `services` entirely. Same literal-value slip family as the Q4 name/namespace mixup.
2. **`-n exam` on `kubectl create clusterrole`.** Silently ignored — ClusterRoles are cluster-scoped and have no namespace. Harmless, but it signals a "`-n` goes on everything" mental model, which is the flip side of the recurring habit of omitting `-n` where it *is* required.
3. **`kubectl auth can-i list pods` with no `--as`.** Checks *your own* (cluster-admin) permissions, not the ServiceAccount's. Returns `yes` unconditionally — even with the RoleBinding deleted.
4. **Stopped at the positive case.** `can-i ... -n exam` → `yes` proves the binding works but not that it's *scoped*. A ClusterRoleBinding — the common wrong answer — produces identical output.
5. **Negative case with no `-n`.** Relies on the current context pointing at `default`. Assumption, not evidence.

### Where `-n` belongs

| Object | Namespaced? | Needs `-n` |
|---|---|---|
| ServiceAccount | yes | **yes** |
| ClusterRole | no (cluster-scoped) | **no** |
| RoleBinding | yes | **yes** |

The namespace inside `--serviceaccount=exam:pod-reader-sa` only says *where the SA lives*. It does not tell the command where to create the new object — that's what `-n` is for.

### Create

```bash
kubectl create sa pod-reader-sa -n exam

kubectl create clusterrole pod-service-reader \
  --verb=get,list,watch \
  --resource=services,pods

kubectl create rolebinding pod-reader-binds \
  --clusterrole=pod-service-reader \
  --serviceaccount=exam:pod-reader-sa \
  -n exam
```

`--clusterrole=` (not `--role=`) on a **RoleBinding** is the "ClusterRole scoped down to one namespace" pattern.

### Verification — all four, in this order

```bash
# 1. Rule contents match the question
kubectl describe clusterrole pod-service-reader

# 2. Binding is in the right namespace and points at a ClusterRole, not a Role
kubectl describe rolebinding pod-reader-binds -n exam

# 3. Positive case
kubectl auth can-i list pods --as=system:serviceaccount:exam:pod-reader-sa -n exam      # yes

# 4. Negative case — explicit namespace
kubectl auth can-i list pods --as=system:serviceaccount:exam:pod-reader-sa -n default   # no
```

Expected output of step 1:

```
PolicyRule:
  Resources  Non-Resource URLs  Resource Names  Verbs
  ---------  -----------------  --------------  -----
  pods       []                 []              [get list watch]
  services   []                 []              [get list watch]
```

### Cleanup (for re-drilling)

```bash
kubectl delete rolebinding pod-reader-binds -n exam
kubectl delete clusterrole pod-service-reader
kubectl delete sa pod-reader-sa -n exam

kubectl get sa,rolebinding -n exam
kubectl get clusterrole pod-service-reader     # should be NotFound
```

ClusterRoles survive namespace-scoped deletes — delete them explicitly or the next attempt inherits the old (possibly wrong) rule.

## Transferable rules

1. **A verification that can't return a failure isn't a verification.** In Q6, steps 1 and 4 are the only ones that can fail. Step 3 alone always looks fine.
2. **Sweep the literals before applying.** Name, namespace, image, counts, command — one by one against the question text, not just the structure. This covers three of the five listed failure patterns.
3. **"Surely this is correct" is the tell.** Every time that thought appeared this session, something was wrong. Assert nothing; show output.
